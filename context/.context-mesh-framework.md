# Context Mesh Framework

Context Mesh is the project memory used by humans and AI agents. It separates
intent from implementation choices and reusable implementation knowledge.

## Framework Overview

The workflow has three steps:

1. **Intent** — describe what the project and its user-facing features are for.
2. **Build** — make changes using approved decisions and documented patterns.
3. **Learn** — record outcomes, new decisions, discoveries and changes.

## File Type Separation

- **Feature files** in `context/intent/feature-*.md` contain only what a feature
  does, why it exists and functional acceptance criteria. They must not contain
  library names, file paths, code examples or technical implementation details.
- **Decision files** in `context/decisions/` contain technical choices,
  rationale, alternatives and outcomes. They explain HOW the system is shaped.
- **Pattern files** in `context/knowledge/patterns/` contain reusable coding
  conventions, implementation guidance and real code examples. They explain
  HOW TO IMPLEMENT.
- **Anti-pattern files** in `context/knowledge/anti-patterns/` document known
  approaches to avoid and why.
- **Agent files** in `context/agents/` contain role-specific operating guidance.
- **Evolution files** record the historical state and lessons learned.

## Plan, Approve, Execute

For material changes, agents must follow this pattern:

1. **Plan** — inspect the relevant intent, decisions and patterns; state the
   proposed change, affected files and validation plan.
2. **Approve** — obtain user approval when the change is consequential,
   ambiguous, destructive or outside the documented intent. Routine scoped
   implementation may proceed when approval is implicit.
3. **Execute** — implement, test, update Context Mesh and report the outcome.

Do not silently convert a feature request into a new technical architecture.
Create or update a decision first when the technical approach is materially new.

## When to Create Files

Create a feature file for a distinct user-facing capability. Create a decision
file for a technical choice that affects architecture, dependencies, interfaces,
security or operations. Create a pattern file when a solution is reusable or a
future contributor needs a concrete implementation example. Do not create
context files for trivial wording changes or duplicate existing knowledge.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/
│   ├── project-intent.md
│   └── feature-*.md
├── decisions/
├── knowledge/
│   ├── patterns/
│   └── anti-patterns/
├── agents/
└── evolution/
```

## Links and Status

Use relative Markdown links. Links should be bidirectional where applicable:
features link to decisions/patterns, decisions link back to features, and
patterns link to related decisions/features. Every context file has a `Status`
section with creation date, lifecycle state and a short note when useful.

## Definition of Done

- Intent is clear and feature descriptions are implementation-independent.
- New technical choices have a decision record.
- Reusable implementation knowledge has a pattern record.
- Bidirectional links are present where relationships exist.
- Code and tests are updated and validated.
- Context and changelog are updated in the same change.
